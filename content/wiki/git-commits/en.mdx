<Sec id="problem" label="01 · Problem">Git is not a backup</Sec>

Many people learn git as a backup: at the end of the day `git add .`, a message like “Update”, `git push`, and the code is safe on the server. That works as long as nobody looks back. A backup cuts by time of day. A commit should cut by content: one change, one reason, one message.

That is what the **staging area** is for, the clipboard between your working copy and the commit. Whatever you put there with `git add` lands in the next commit, everything else stays where it is. If you always put everything in, you throw away exactly this choice.

You can see the result above at the end of the animation. With four commits, `git log --grep=timeout` finds the fix right away, and `git revert` undoes the header without restoring the contact page. With the one catch-all commit, neither works.

This applies even if you work on a project alone. Your future self is the colleague who no longer has the code in their head. In a team, you also mostly read commits you did not write yourself.

The most common objection: “Then the log is full of tiny commits.” A commit that only changes a background color is still a good commit. And if the many small commits feel like too much before the merge, you combine them with one command (step 4 below). The reverse, splitting a big commit afterward, means resetting and re-sorting every line.

<Sec id="praxis" label="03 · Practice">How to commit in daily work</Sec>

I ran all commands in a fresh repository with git 2.43. The script that goes with it plays through every step automatically.

### 1. Look first, then select

Before you stage anything, get an overview. `git status` shows which files changed, `git diff` shows the lines. Then you deliberately stage what belongs together:

<Code file="Terminal">
```sh
git status
# only the two files for the contact page
git add pages/kontakt.html templates/footer.html
# check what actually ends up in the commit
git diff --cached --stat
```
</Code>

### 2. Separate two changes in one file

Often two topics sit in the same file. `git add -p` goes through the changes hunk by hunk and asks each time: `y` takes the hunk, `n` leaves it, `s` splits it into smaller ones, `e` opens it for editing.

<Code file="git add -p · output shortened">
```text
$ git add -p app.py
@@ -1,6 +1,6 @@
 def timeout():
-    return 30
+    return 60
 ...
-    return "Hello"
+    return "Hello, world"
(1/1) Stage this hunk [y,n,q,a,d,s,e,?]? s
Split into 2 hunks.
# first part (timeout): y, second part (greeting): n

$ git diff --cached
-    return 30
+    return 60
```
</Code>

Only the timeout lands in the commit. The greeting stays in your working copy for the next commit.

### 3. Write the message

Without `-m`, `git commit` opens your editor, and you write the subject, blank line and body as above. For short messages from the terminal you can also use `-m` twice: the first becomes the subject, the second the body, and git adds the blank line itself.

<Code file="Terminal">
```sh
git commit -m "chore(site): Remove contact page" \
  -m "Requests have gone through the footer form since the relaunch."

# check the result
git log -1 --format=%B
```
</Code>

So that nobody forgets the form, put a template in the repository. git shows it in the editor every time, and lines starting with `#` do not end up in the message:

<Code file=".gitmessage">
```text

# type(scope): what the commit does, max. 50 characters
# Types: feat fix docs refactor test build ci chore perf revert
#
# Why is the change needed? What was the problem before?
#
# Refs: TICKET-123
```
</Code>

<Code file="Terminal · once per clone">
```sh
git config commit.template .gitmessage
# additionally shows the diff below the template in the editor
git config commit.verbose true
```
</Code>

### 4. Improve a commit without clogging the log

During review you notice that 60 seconds is not enough, it has to be 90. Instead of a new commit “Adjust timeout again”, you mark the correction as an addendum to the original commit. Before the merge, git folds it in.

<Code file="Terminal">
```sh
git log --oneline        # find the hash of the target commit, e.g. 91fd3b7
git add src/session/config.py
git commit --fixup=amend:91fd3b7
# the editor opens: change body and subject to 90 seconds,
# but leave the first line "amend! ..." as it is

git rebase -i --autosquash main
# the list is already sorted: save and close
```
</Code>

Afterward there is a single commit “fix(session): Raise timeout to 90 seconds” with the right content. If the old message is fine, use `--fixup=91fd3b7` without `amend:`. You combine several small commits the same way: in the list of `git rebase -i`, replace `pick` with `fixup` or `squash`.

<Callout variant="warning" title="Only on your branch">
Rebase rewrites commits. Do it only on your own feature branch, before it lands in `main`. If you rewrite commits that others have already pulled, you mess up their clones.
</Callout>

### 5. Secure the format in the team

An agreement in the wiki lasts two weeks. A hook lasts longer: a script that git runs before every commit. The `commit-msg` hook receives the message as a file and can reject the commit with an error code. This version checks type, scope and length, and lets git-generated messages such as `Merge`, `Revert` and `fixup!` through:

<Code file=".githooks/commit-msg">
```sh
#!/bin/sh
# Checks the first line of the commit message against Conventional Commits.
# Location: .githooks/commit-msg, enable with: git config core.hooksPath .githooks
msg_file="$1"
subject=$(grep -v '^#' "$msg_file" | head -n 1)

# Let git-generated messages through
case "$subject" in
  Merge\ *|Revert\ *|fixup!\ *|squash!\ *|amend!\ *) exit 0 ;;
esac

pattern='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .+'
if ! printf '%s\n' "$subject" | grep -Eq "$pattern"; then
  echo "Commit rejected: \"$subject\"" >&2
  echo "Format: type(scope): description, e.g. fix(login): End session after timeout" >&2
  exit 1
fi

# Count characters, not bytes: non-ASCII characters such as "ü" take two bytes in UTF-8
len=$(printf '%s' "$subject" | LC_ALL=C.UTF-8 wc -m)
if [ "$len" -gt 72 ]; then
  echo "Commit rejected: first line has $len characters, the limit is 72." >&2
  echo "Tip: If it does not fit on one line, the commit usually contains more than one change." >&2
  exit 1
fi
if [ "$len" -gt 50 ]; then
  echo "Note: first line has $len characters, target is 50." >&2
fi
```
</Code>

Above 50 characters the hook only gives a note, above 72 it rejects. The type and scope already cost 10 to 15 characters, so a hard limit at 50 would trigger too often. The hook goes into the repository with the execute permission, and then everyone activates it once in their clone:

<Code file="Terminal">
```sh
chmod +x .githooks/commit-msg
git update-index --chmod=+x .githooks/commit-msg   # if it was already committed without the permission
git add .githooks && git commit -m "build(git): Add commit message hook"

# everyone on the team, once per clone
git config core.hooksPath .githooks
```
</Code>

<Code file="Output in the test">
```text
$ git commit -m "fixed stuff"
Commit rejected: "fixed stuff"
Format: type(scope): description, e.g. fix(login): End session after timeout

$ git commit -m "fix(session): Force logout after timeout without prompt"
Note: first line has 55 characters, target is 50.

$ git commit -m "feat(api)!: Remove endpoint v1"
[main 7230073] feat(api)!: Remove endpoint v1
```
</Code>

A local hook is a help, not a control: `git commit --no-verify` skips it. If you want to make the format binding, also check the messages in the CI pipeline of the pull request. I did not set that up here.

### 6. Write down the agreement

The hook checks the form, not the split. What a commit should contain belongs in the repository as a short rule, for example in `CONTRIBUTING.md`:

<Code file="CONTRIBUTING.md · excerpt">
```md
## Commits
- One commit = one change with one reason. When in doubt, smaller.
- First line: type(scope): what the commit does, max. 50 characters.
- Body when the why is not obvious. Ticket in the last line.
- Improvements before the merge with --fixup and rebase --autosquash.
- Once per clone: git config core.hooksPath .githooks
```
</Code>

<Sec id="entscheidung" label="05 · Decision">How big is a commit?</Sec>

| Situation | How you commit | Why |
| --- | --- | --- |
| Changed one color in the header | One commit of its own | Small is not a problem. You can find and revert it on its own. |
| New feature across five files | One commit, if all five are needed for the feature | Half a commit would break the build or link to nothing. |
| Fixed a bug and renamed something on the side | Two commits, the rename first | The fix stays readable in the diff and can be reverted on its own. |
| Reformatted a whole file | Own commit before the content change | Otherwise one changed line hides among a hundred moved ones. |
| End of the day, half done | Interim state on your branch, fold before the merge | It is backed up anyway, only `main` never sees it. |
| Test for the fix | In the same commit as the fix | The fix and its check belong together, also on revert. |

<Callout variant="tip" title="Rule of thumb">
Read your subject line out loud. If you need “and” for it, it is two commits. If you do not know what to write, you do not yet know what the commit does.
</Callout>
