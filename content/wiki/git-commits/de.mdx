<Sec id="problem" label="01 · Problem">Git ist kein Backup</Sec>

Viele lernen git als Sicherung: Am Ende des Tages `git add .`, eine Nachricht wie „Update“, `git push`, und der Code liegt sicher auf dem Server. Das funktioniert, solange niemand zurückschaut. Ein Backup schneidet nach der Uhrzeit. Ein Commit soll nach dem Inhalt schneiden: eine Änderung, ein Grund, eine Nachricht.

Dafür gibt es den **Staging-Bereich**, die Zwischenablage zwischen Arbeitskopie und Commit. Was du mit `git add` dort hineinlegst, landet im nächsten Commit, alles andere bleibt liegen. Wer immer alles hineinlegt, verschenkt genau diese Auswahl.

Das Ergebnis siehst du oben am Ende der Animation. Mit vier Commits findet `git log --grep=Timeout` den Fix sofort, und `git revert` nimmt den Header zurück, ohne die Kontaktseite wiederherzustellen. Mit dem einen Sammel-Commit geht beides nicht.

Das gilt auch, wenn du allein an einem Projekt arbeitest. Dein zukünftiges Ich ist der Kollege, der den Code nicht mehr im Kopf hat. Im Team kommt dazu, dass du überwiegend Commits liest, die du nicht selbst geschrieben hast.

Der häufigste Einwand: „Dann ist das Log voller winziger Commits.“ Ein Commit, der nur eine Hintergrundfarbe ändert, ist trotzdem ein guter Commit. Und wem die vielen kleinen Commits vor dem Merge zu viel sind, fasst sie mit einem Befehl zusammen (Schritt 4 unten). Der umgekehrte Weg, einen großen Commit nachträglich aufzuteilen, heißt: zurücksetzen und jede Zeile neu sortieren.

Nicht jeder Commit braucht alle fünf Teile. Ein korrigierter Tippfehler kommt mit der ersten Zeile aus. Sobald die Frage „Warum?“ nicht offensichtlich ist, gehört die Antwort in den Body.

<Sec id="praxis" label="03 · Praxis">So committest du im Alltag</Sec>

Alle Befehle habe ich in einem frischen Repository mit git 2.43 ausgeführt. Das Skript dazu spielt jeden Schritt automatisch durch.

### 1. Erst schauen, dann auswählen

Bevor du etwas stagest, verschaff dir einen Überblick. `git status` zeigt, welche Dateien sich geändert haben, `git diff` zeigt die Zeilen. Dann legst du gezielt in den Staging-Bereich, was zusammengehört:

<Code file="Terminal">
```sh
git status
# nur die zwei Dateien zur Kontaktseite
git add pages/kontakt.html templates/footer.html
# prüfen, was wirklich im Commit landet
git diff --cached --stat
```
</Code>

### 2. Zwei Änderungen in einer Datei trennen

Oft stecken zwei Themen in derselben Datei. `git add -p` geht die Änderungen Abschnitt für Abschnitt durch und fragt jedes Mal: `y` nimmt den Abschnitt, `n` lässt ihn liegen, `s` teilt ihn in kleinere, `e` öffnet ihn zum Bearbeiten.

<Code file="git add -p · Ausgabe gekürzt">
```text
$ git add -p app.py
@@ -1,6 +1,6 @@
 def timeout():
-    return 30
+    return 60
 ...
-    return "Hallo"
+    return "Hallo, Welt"
(1/1) Stage this hunk [y,n,q,a,d,s,e,?]? s
Split into 2 hunks.
# erster Teil (Timeout): y, zweiter Teil (Begrüßung): n

$ git diff --cached
-    return 30
+    return 60
```
</Code>

Im Commit landet nur der Timeout. Die Begrüßung bleibt in der Arbeitskopie für den nächsten Commit.

### 3. Die Nachricht schreiben

Ohne `-m` öffnet `git commit` deinen Editor, und du schreibst Betreff, Leerzeile und Body wie oben. Für kurze Nachrichten aus dem Terminal geht es auch mit zweimal `-m`: Das erste wird der Betreff, das zweite der Body, die Leerzeile setzt git selbst.

<Code file="Terminal">
```sh
git commit -m "chore(site): Kontaktseite entfernen" \
  -m "Anfragen laufen seit dem Relaunch über das Formular im Footer."

# Ergebnis prüfen
git log -1 --format=%B
```
</Code>

Damit niemand die Form vergisst, legt ihr eine Vorlage ins Repository. git zeigt sie jedes Mal im Editor an, Zeilen mit `#` landen nicht in der Nachricht:

<Code file=".gitmessage">
```text

# typ(bereich): was der Commit bewirkt, max. 50 Zeichen
# Typen: feat fix docs refactor test build ci chore perf revert
#
# Warum ist die Änderung nötig? Was war vorher das Problem?
#
# Refs: TICKET-123
```
</Code>

<Code file="Terminal · einmal pro Klon">
```sh
git config commit.template .gitmessage
# zeigt im Editor zusätzlich den Diff unter der Vorlage
git config commit.verbose true
```
</Code>

### 4. Nachbessern, ohne das Log zu verstopfen

Beim Review fällt auf: 60 Sekunden reichen nicht, es müssen 90 sein. Statt eines neuen Commits „Timeout nochmal angepasst“ markierst du die Korrektur als Nachtrag zum ursprünglichen Commit. Vor dem Merge faltet git sie hinein.

<Code file="Terminal">
```sh
git log --oneline        # Hash des Ziel-Commits suchen, z. B. 91fd3b7
git add src/session/config.py
git commit --fixup=amend:91fd3b7
# Editor öffnet sich: Body und Betreff auf 90 Sekunden ändern,
# die erste Zeile "amend! ..." aber stehen lassen

git rebase -i --autosquash main
# die Liste ist schon sortiert: speichern und schließen
```
</Code>

Danach gibt es einen einzigen Commit „fix(session): Timeout auf 90 Sekunden erhöhen“ mit dem richtigen Inhalt. Reicht die alte Nachricht, nimmst du `--fixup=91fd3b7` ohne `amend:`. Genauso fasst du mehrere kleine Commits zusammen: In der Liste von `git rebase -i` ersetzt du `pick` durch `fixup` oder `squash`.

<Callout variant="warning" title="Nur auf deinem Branch">
Rebase schreibt Commits neu. Mach das nur auf deinem eigenen Feature-Branch, bevor er in `main` landet. Wer Commits neu schreibt, die andere schon geholt haben, bringt deren Klone durcheinander.
</Callout>

### 5. Das Format im Team absichern

Eine Vereinbarung im Wiki hält zwei Wochen. Ein Hook hält länger: ein Skript, das git vor jedem Commit ausführt. Der `commit-msg`-Hook bekommt die Nachricht als Datei und kann den Commit mit einem Fehlercode ablehnen. Diese Fassung prüft Typ, Bereich und Länge und lässt von git erzeugte Nachrichten wie `Merge`, `Revert` und `fixup!` durch:

<Code file=".githooks/commit-msg">
```sh
#!/bin/sh
# Prüft die erste Zeile der Commit-Nachricht gegen Conventional Commits.
# Ablage: .githooks/commit-msg, aktivieren mit: git config core.hooksPath .githooks
msg_file="$1"
subject=$(grep -v '^#' "$msg_file" | head -n 1)

# Von git erzeugte Nachrichten durchlassen
case "$subject" in
  Merge\ *|Revert\ *|fixup!\ *|squash!\ *|amend!\ *) exit 0 ;;
esac

pattern='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9-]+\))?!?: .+'
if ! printf '%s\n' "$subject" | grep -Eq "$pattern"; then
  echo "Commit abgelehnt: \"$subject\"" >&2
  echo "Format: typ(bereich): beschreibung, z. B. fix(login): Sitzung nach Timeout beenden" >&2
  exit 1
fi

# Zeichen zählen, nicht Bytes: Umlaute sind in UTF-8 zwei Bytes lang
len=$(printf '%s' "$subject" | LC_ALL=C.UTF-8 wc -m)
if [ "$len" -gt 72 ]; then
  echo "Commit abgelehnt: erste Zeile hat $len Zeichen, erlaubt sind 72." >&2
  echo "Tipp: Passt es nicht in eine Zeile, steckt meist mehr als eine Änderung im Commit." >&2
  exit 1
fi
if [ "$len" -gt 50 ]; then
  echo "Hinweis: erste Zeile hat $len Zeichen, Ziel sind 50." >&2
fi
```
</Code>

Über 50 Zeichen gibt der Hook nur einen Hinweis, über 72 lehnt er ab. Der Typ und der Bereich kosten schon 10 bis 15 Zeichen, eine harte Grenze bei 50 würde zu oft greifen. Ins Repository kommt der Hook mit Ausführungsrecht, danach aktiviert ihn jeder einmal in seinem Klon:

<Code file="Terminal">
```sh
chmod +x .githooks/commit-msg
git update-index --chmod=+x .githooks/commit-msg   # falls schon ohne Recht eingecheckt
git add .githooks && git commit -m "build(git): Hook für Commit-Nachrichten"

# jeder im Team, einmal pro Klon
git config core.hooksPath .githooks
```
</Code>

<Code file="Ausgabe im Test">
```text
$ git commit -m "fixed stuff"
Commit abgelehnt: "fixed stuff"
Format: typ(bereich): beschreibung, z. B. fix(login): Sitzung nach Timeout beenden

$ git commit -m "fix(session): Abmeldung nach Timeout erzwingen ohne Rückfrage"
Hinweis: erste Zeile hat 61 Zeichen, Ziel sind 50.

$ git commit -m "feat(api)!: Endpunkt v1 entfernen"
[main 7230073] feat(api)!: Endpunkt v1 entfernen
```
</Code>

Ein lokaler Hook ist eine Hilfe, keine Kontrolle: `git commit --no-verify` überspringt ihn. Wer das Format verbindlich machen will, prüft die Nachrichten zusätzlich in der CI-Pipeline des Pull Requests. Das habe ich hier nicht aufgesetzt.

### 6. Die Vereinbarung aufschreiben

Der Hook prüft die Form, nicht den Schnitt. Was ein Commit enthalten soll, gehört als kurze Regel ins Repository, zum Beispiel in die `CONTRIBUTING.md`:

<Code file="CONTRIBUTING.md · Ausschnitt">
```md
## Commits
- Ein Commit = eine Änderung mit einem Grund. Im Zweifel kleiner.
- Erste Zeile: typ(bereich): was der Commit bewirkt, max. 50 Zeichen.
- Body, wenn das Warum nicht offensichtlich ist. Ticket in die letzte Zeile.
- Nachbesserungen vor dem Merge mit --fixup und rebase --autosquash.
- Einmal pro Klon: git config core.hooksPath .githooks
```
</Code>

<Sec id="entscheidung" label="05 · Entscheidung">Wie groß ist ein Commit?</Sec>

| Situation | So committest du | Warum |
| --- | --- | --- |
| Eine Farbe im Header geändert | Ein eigener Commit | Klein ist kein Problem. Man findet und revertiert ihn einzeln. |
| Neue Funktion über fünf Dateien | Ein Commit, wenn alle fünf für die Funktion nötig sind | Ein halber Commit würde den Build brechen oder ins Leere verlinken. |
| Fehler behoben und nebenbei umbenannt | Zwei Commits, zuerst das Umbenennen | Der Fix bleibt im Diff lesbar und lässt sich einzeln zurücknehmen. |
| Ganze Datei neu formatiert | Eigener Commit vor der inhaltlichen Änderung | Sonst versteckt sich eine geänderte Zeile zwischen hundert verschobenen. |
| Feierabend, halb fertig | Zwischenstand auf deinem Branch, vor dem Merge falten | Gesichert ist er trotzdem, nur `main` sieht ihn nie. |
| Test zum Fix | Im selben Commit wie der Fix | Fix und Prüfung gehören zusammen, auch beim Revert. |

<Callout variant="tip" title="Faustregel">
Lies deine Betreffzeile laut. Wenn du dafür „und“ brauchst, sind es zwei Commits. Wenn du nicht weißt, was du schreiben sollst, weißt du noch nicht, was der Commit tut.
</Callout>
